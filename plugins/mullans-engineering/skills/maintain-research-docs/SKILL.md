# Maintain research docs

Review reference organization using the project's existing placement, unit and
maintenance conventions. Discover its procedure and tooling before choosing
commands; preserve established review sets, thresholds and approval boundaries.
Existing tooling owns discovery, measurements, source validation, selective
commits and revision discovery; use its interfaces rather than duplicating them
in new scripts or instructions. For current-session findings, use
`research-promotion` instead. Maintenance does not authorize new investigations
or live tests. Skill invocation alone does not approve restructuring or commits.

## 1. Identify the maintenance scope

Read applicable instructions and relevant reference navigation. For an already
approved batch with execution authorization, proceed to its source validation
and application without requesting approval again. For a new audit, use existing
tooling and its defined recursive reference/registered-path review set; otherwise
inspect the requested reference set with bounded reads.

Load project placement policy when judging ownership/splits, reference-unit
conventions when editing units, evidence/catalog guidance when reviewing support,
and maintenance procedure when auditing, proposing, committing or finalizing.
Report measurement errors rather than treating them as an empty review set.

Done: the review set or approved batch, relevant conventions, execution
authorization and measurement gaps are identified.

## 2. Review and propose

Assess flagged or requested pages for ownership, redundancy, discovery, misplaced
history/procedures/state and coherent split boundaries. Size thresholds trigger
judgment, not an automatic split. Verify support before changing technical claims;
organizational checks do not certify scientific correctness.

Review every audit-flagged item. Prepare concrete patches and a summary in the
owning investigation, including source/output identities, relocation/link changes,
evidence issues and each item's disposition. Use existing proposal tooling when
available and keep draft copies excluded from maintained-reference retrieval. Review affected support
before changing substantive evidence fingerprints; do not reset them merely to
clear warnings. Collect unresolved technical conflicts for one user decision round. Preserve original
evidence and stable finding IDs.

Present the proposal for approval before restructuring unless the exact batch is
already authorized. Keep pending/rejected items visible; they do not become
accepted review baselines. A sufficient reference set may require no changes.

Done: every audit-flagged or requested item has a justified disposition or
explicit gap, needed patches are reviewable, and pending approvals or evidence
gaps are presented.

## 3. Apply an approved batch

Revalidate source and patch identities immediately before application. Reconcile
changed sources or outputs with the approved scope; obtain renewed review when
the approved result no longer applies.

Apply only approved changes, repair inbound navigation, and run established
citation, catalog and link checks. Review factual support separately from structure.
Use existing selective-commit infrastructure, preserving unrelated work and
staged entries; hold overlapping changes that cannot be separated safely. Commit
under project instructions.

When a registry/finalization workflow exists, commit approved documents first, then
finalize the approved batch together. Let the existing tool discover document
revisions; do not finalize one document at a time or supply individual revisions
instead. Wait for each dependent operation before starting the next. Commit
finalized registry metadata separately. Keep held locks, missing baselines, stale
approvals and conflicts visible under the existing safeguards.

Keep review history, verification, commits and unresolved items in the owning
investigation. Reference pages retain facts, contracts, applicability and limits.

Done: approved changes and links are verified, required commits/finalization are
complete, and every held item or unfinished stage has an explicit reason.
