# Skills platform audit for session-learning 0.7.0

Reviewed on 2026-10-03. This is a maintainer report, outside distributable skills.

## Finding and scope

Storing mutable project state under `.agents/learning` contradicted Codex's default protected-path policy. This is a cross-platform design error; Windows exposed it through filesystem permissions. Existing workspace `.agents` and `.codex` directories are recursively protected. Ordinary writable roots do not override those exceptions. Moving the project store to `.session-learning` removes that conflict without changing permissions. [Protected paths and OS enforcement](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots).

The audit covered all seven distributed skill entry points, host wiring guidance, session-learning readers/writers, hook adapters, manifests, and runtime prerequisites. It checked the platform contract rather than attempting a security audit of every bundled utility. No other mutable project learning location remains. Personal local authority is still guidance scoped to a hashed project root, not global memory.

## Native permission check procedure

Use `tools/session-learning/check_storage_permissions.py`, outside the shipped skill. Prepare a fresh fixture from the user's normal terminal, before entering a sandbox, with `--prepare --root <absolute-fixture-root>`. The fixture contains preexisting `.agents` and `.codex` directories and an existing `.session-learning/probe.json`. Never point it at real configuration or personal stores. Use a repository `temp_<os>_live_fixture` directory.

Run the check in an ordinary workspace sandbox rooted at that fixture. Expected results: replacement of the existing project-state file succeeds, a validation failure restores the preceding bytes, the final file returns to its original bytes, and writes into both protected directories are denied. A failing check must not be relabeled successful because the same operation works elevated. Unit failure injection additionally checks later-target denial, incomplete rollback retention, and interrupted recovery.

Use installed help when documentation and executable syntax differ. No sandbox/profile/ACL configuration was changed for this effort.

Earlier permission-probe children and the interrupted check's child were checked and stopped or confirmed absent. Actual home-store writes were not tested; isolated local-authority fixtures validate routing only.

## Windows replacement retry follow-up

Further isolated checks showed intermittent failures even outside the sandbox: 14/100 rapid replacements failed under ordinary permissions and 12/100 failed elevated. Read/write/delete handle-access checks succeeded. This supports a timing-sensitive Windows interaction rather than a fixed protected-path denial; no locking process or exact cause was identified. Microsoft documents relevant [file-sharing and replacement behavior](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files). The observation must not be generalized into a failure rate for other machines.

The shared atomic-write helper now retries the same completed temporary file on Windows errors 5, 32, and 33. It uses increasing delays starting at 25 ms, capped at 200 ms, with a one-second retry deadline and at most eight attempts. Unrelated errors and non-Windows failures return immediately. Persistent failures retain their exception type/error code and identify the replacement target and attempt count. No destination-first deletion or direct-overwrite fallback is permitted. The deadline bounds retries, not time spent inside a blocked operating-system call.

Rollback and interrupted recovery use this same helper. Incomplete rollback still retains its journal and backups. Agents receive one script result; the skill adds no agent-managed sleep/retry procedure. Advisory hook deadlines and failure-open behavior remain applicable if the host terminates an operation.

Five deterministic regression tests cover transient success, reuse of the completed temporary file, permanent denial, deadline/attempt bounds, unrelated errors, non-Windows behavior, unchanged destination/temporary cleanup, rollback, retained evidence, and recovery. The full session-learning suite passes 218 tests.

The maintainer permission checker supports `--repeat 100 --windows-lock-check --writes-only` on a fresh prepared fixture. In this session, all 100 replacements and 100 rollbacks passed under ordinary Windows workspace permissions. A native handle held without delete-sharing produced safe bounded failure; releasing a lock during replacement allowed automatic success. The checker restored original bytes. These results supersede the earlier failed replacement acceptance check for this environment; elevated comparisons remain separate. Repeat these native checks when changing transaction behavior. macOS/Linux execution remains unverified, and the exact transient interference source remains unknown.
